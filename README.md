# 부산 로컬페이 관광 소비 루트 (가칭)

> KB Bridge 파이널 프로젝트 · 지역상생금융 / 지역경제 활성화

부산을 찾은 외국인 자유여행객이 지역화폐(부산페이·동백전)로 결제할 수 있는 매장을 찾아 동선에 맞는 소비 루트를 계획하도록 돕고, 같은 데이터로 소상공인에게 지역화폐·QR 도입 효과 시나리오를 보여주는 모바일 웹 서비스입니다.

- 기획 문서: [`docs/KB_Bridge_PRD_부산로컬페이루트_v0.3.docx`](docs/) (PRD, DB 스키마는 부록 B, CSV 템플릿은 부록 C)
- 기술 스택: PostgreSQL · pandas · Streamlit · n8n (Telegram)
- 일정: PRD 초안 10/16 → 컨펌 10/19~23 → 기술 멘토링 10/27~28 → **최종 제출 11/4 10:00** → 발표 11/5

## 2. 프로젝트 진행 틀

### 2.1 작업 흐름 (워크스트림 5개)

```
[기획·PO] ──── 범위·일정·발표 ───────────────────────────────┐
                                                               ▼
[데이터 A·B] ─ 원천 수집 → CSV 템플릿 → validate ─┐       [통합·시연]
                                                   ▼            ▲
[개발] ─────── 스키마 → 적재(build) → 추천·화면 ─┴──── 배포 ───┤
                                                   ▲            │
[디자인·콘텐츠] ─ 와이어프레임·번역·문구 ─────────┘            │
                                                                │
[자동화·QA] ── n8n·텔레그램 → QA → 사용성 테스트 ───────────────┘
```

핵심은 **"약속(인터페이스)을 먼저 정하고 각자 병렬로 일한다"**입니다. 개발 리드가 1주차 초에 아래 세 가지를 공개하면, 나머지 팀원은 개발을 기다리지 않고 동시에 작업합니다.

1. **DB 스키마 + CSV 템플릿** (PRD 부록 B·C) → 데이터 A·B
2. **번역 키 목록** (`i18n_ui.csv`의 `key`) → 콘텐츠·다국어
3. **n8n webhook으로 보낼 JSON 형식** → 자동화·QA

GitHub **Milestone**으로 만들고, 모든 이슈는 셋 중 하나에 속합니다.

- 이슈 하나는 **한 사람이 1~3일 안에 끝낼 크기**로 쪼갭니다.
- GitHub **Projects 보드** 컬럼: `Backlog` → `To Do` → `In Progress` → `Review` → `Done`
- 라벨

## 4. 형상관리 규칙

형상관리 대상은 **코드만이 아닙니다.** 이 프로젝트에서는 아래 네 가지를 모두 git으로 관리합니다.

| 대상 | 관리 방법 |
|---|---|
| 코드 | 브랜치 → PR → 리뷰 → 머지 |
| DB 스키마 | `db/migrations/`에 번호 붙은 SQL 파일로만 변경, 기존 파일 수정 금지 |
| 데이터 | `data/manual/` CSV는 PR로 제출, `data/raw/` 원본은 해시를 `MANIFEST.csv`에 기록 |
| 문서 | PRD·회의록·결정 기록을 `docs/`에 커밋, 범위 변경은 PRD 9.3에도 기록 |

### 4.1 브랜치 전략 (GitHub Flow)

- `main`은 **항상 시연 가능한 상태**입니다. `main`에 직접 push하지 않습니다 (브랜치 보호 설정).
- 작업 브랜치는 `main`에서 만들고, 끝나면 PR로 합칩니다.

| 접두어 | 용도 | 예시 |
|---|---|---|
| `feat/` | 기능 | `feat/12-route-recommend` |
| `fix/` | 버그 수정 | `fix/31-telegram-retry` |
| `data/` | 데이터 CSV 추가·수정 | `data/18-qr-check-haeundae` |
| `docs/` | 문서 | `docs/7-prd-v0.4` |
| `design/` | 디자인 자료 | `design/20-wireframe-s05` |
| `chore/` | 설정·의존성 | `chore/3-ci-validate` |

형식: `<접두어>/<이슈번호>-<짧은-영문-설명>`

### 4.2 커밋 메시지

```
<type>(<범위>): <무엇을 했는지 한 줄, 한국어 가능>

<필요하면 왜 바꿨는지>

Refs #<이슈번호>
```

| type | 언제 |
|---|---|
| `feat` | 기능 추가 |
| `fix` | 버그 수정 |
| `data` | 데이터 파일 추가·수정 |
| `db` | 스키마·마이그레이션 |
| `docs` | 문서 |
| `design` | 디자인 자료 |
| `test` | 테스트 |
| `refactor` | 동작 변화 없는 코드 정리 |
| `chore` | 설정·빌드·의존성 |

예시
```
feat(F-01): 결제 방법(QR) 선택 시 QR 확인 매장 우선 추천

Refs #12
```
```
data(qr): 해운대 QR 수동 검증 25곳 추가

Refs #18
```

규칙
- **커밋 하나에는 한 가지 변경만** 담습니다. "이것저것 수정" 같은 커밋은 만들지 않습니다.
- 동작하지 않는 코드는 `main`에 들어가지 않게 합니다 (브랜치 안에서는 자유).

### 4.3 Pull Request

- **PR 하나 = 이슈 하나.** 본문에 `Closes #이슈번호`를 적어 머지 시 이슈가 자동으로 닫히게 합니다.
- PR 본문에 적을 것: 무엇을 바꿨는지, 어떻게 확인했는지(스크린샷·실행 결과), 영향 범위
- 리뷰 규칙

| PR 종류 | 리뷰어 | 머지 조건 |
|---|---|---|
| 코드 (`feat` `fix`) | 자동화·QA 1명 (동작 확인) | 실행 확인 + CI 통과 |
| 데이터 (`data`) | 데이터 짝꿍 1명 + 개발 리드 | `validate.py` CI 통과 |
| 스키마 (`db`) | 개발 리드 + 데이터 A·B 공유 | PRD 9.3 변경 기록 |
| 문서·디자인 | 기획·PO | 1명 승인 |

- 머지 방식: **Squash and merge** (PR 하나가 `main`에 커밋 하나로 남아 이력이 깔끔해집니다)
- 머지는 개발 리드가 합니다. 충돌이 나면 PR 작성자가 먼저 `main`을 반영해 해결합니다.

### 4.4 데이터 형상관리

- `data/raw/`의 공공데이터 원본은 용량 때문에 **git에 올리지 않고** 팀 공유 드라이브에 둡니다. 대신 `data/raw/MANIFEST.csv`에 `파일명, 출처 URL, 다운로드일, 데이터기준일자, sha256`을 커밋합니다. 누가 어떤 원본으로 적재했는지 재현할 수 있게 하기 위해서입니다.
- `data/manual/`의 팀원 CSV는 **git으로 버전 관리**합니다. 템플릿은 PRD 부록 C를 따릅니다.
- `benefit_policy.csv`와 `scenario_assumption.csv`는 **기존 행을 고치지 않고** 새 버전 행을 추가합니다.
- CI(GitHub Actions)에서 PR마다 `validate.py`가 돌아 컬럼·허용값·날짜 형식을 검사합니다. 실패하면 머지할 수 없고, **제출한 사람이 고칩니다.**

### 4.5 DB 스키마 변경

1. 이슈를 만들고 PRD 9.3 변경 이력에 한 줄 추가
2. `db/migrations/NNN_설명.sql` 새 파일 작성 (이미 머지된 마이그레이션 파일은 수정 금지)
3. `db/schema.sql`을 최신 상태로 갱신
4. `db/` PR → 데이터 담당에게 공유 후 머지

### 4.6 태그와 릴리스

중요한 시점마다 태그를 남겨, 언제든 그 상태로 돌아갈 수 있게 합니다.

| 태그 | 시점 | 의미 |
|---|---|---|
| `v0.1-data` | 10/23 | 데이터 적재·매칭 완료 |
| `v0.5-p0` | 10/30 | P0 기능 동작 |
| `v0.9-freeze` | 11/2 | 기능 동결, 이후 버그 수정만 |
| `v1.0-submit` | 11/4 | 최종 제출본 |
| `v1.0-demo` | 11/5 | 발표 시연본 |

### 4.7 비밀값과 개인정보

- API 키, Telegram 봇 토큰, n8n webhook URL, DB 접속 정보는 **절대 커밋하지 않습니다.** `.env`에 두고, `.env.example`에는 이름만 적습니다.
- n8n 워크플로를 export할 때 credential과 webhook URL을 지우고 커밋합니다.
- 실수로 커밋했다면 바로 개발 리드에게 알리고 **해당 키를 재발급**합니다. 커밋을 지우는 것만으로는 부족합니다.
- 실명, 연락처, 텔레그램 chat_id, 인터뷰 원본 녹음은 레포에 올리지 않습니다.

### 4.8 회의록과 결정 기록

- 회의록: `docs/meetings/YYYY-MM-DD.md` (참석자 역할, 결정 사항, 할 일과 담당 이슈 번호)
- 범위·스키마·일정이 바뀌는 결정은 `docs/decisions.md`와 PRD 9.3에 함께 기록합니다. 기능을 추가하면 **무엇을 뺄지도** 적습니다.

### 4.9 개발자가 아닌 팀원을 위한 방법

git 명령어를 몰라도 됩니다. 셋 중 편한 방법을 쓰세요.

1. **GitHub 웹**: 레포에서 `Add file → Upload files` → "Create a new branch" 선택 → PR 생성
2. **GitHub Desktop**: 브랜치 만들기 → 파일 수정 → Commit → Push → Create Pull Request
3. **AI 도구(Claude Code 등)**: 아래 5장의 프롬프트를 그대로 사용

## 5. AI에게 형상관리를 맡길 때

### 5.1 원칙

AI는 규칙을 알려 주면 잘 따르지만, 알려 주지 않으면 `main`에 바로 커밋하거나 여러 작업을 한 커밋에 섞기 쉽습니다. 다음 네 가지를 항상 지키세요.

1. **규칙 위치를 알려 주기**: "README.md 4장 형상관리 규칙을 따라" 한 줄이면 됩니다.
2. **범위를 하나로 제한하기**: 이슈 번호 하나, 파일 범위를 명시합니다.
3. **금지 사항을 적기**: main 직접 push, force push, `.env`·원본 데이터 커밋, 다른 사람 파일 수정 금지
4. **실행 전에 확인받기**: 커밋·push·PR 전에 변경 내용(diff)과 커밋 메시지를 먼저 보여 달라고 합니다.

> 팁: 레포 루트에 `CLAUDE.md`(또는 `AGENTS.md`)를 만들고 "형상관리는 README.md 4장을 따른다"와 아래 금지 사항을 적어 두면, 매번 프롬프트에 쓰지 않아도 AI가 자동으로 읽고 따릅니다.

### 5.2 상황별 프롬프트

**작업 시작**
```
README.md 4장 형상관리 규칙을 따라줘.
이슈 #12 "결제 방법 QR 선택 시 추천 우선순위" 작업을 시작할 거야.
main을 최신으로 받은 뒤 규칙에 맞는 브랜치를 만들어줘.
아직 파일은 수정하지 마.
```

**커밋**
```
README.md 4장 규칙대로 커밋해줘.
1. 먼저 git status와 diff를 요약해서 보여줘.
2. 변경이 여러 종류면 커밋을 나눠야 하는지 제안해줘.
3. 커밋 메시지 초안(type(범위): 설명 + Refs #12)을 보여주고 내가 확인하면 커밋해.
.env, data/raw/ 파일은 절대 커밋하지 마. push는 아직 하지 마.
```

**PR 만들기**
```
현재 브랜치를 push하고 main으로 PR을 만들어줘.
PR 본문에는 무엇을 바꿨는지, 어떻게 확인했는지, 영향 범위, "Closes #12"를 넣어줘.
라벨은 area:app, P0, 마일스톤은 W2 핵심 구현으로 해줘.
만들기 전에 제목과 본문을 먼저 보여줘.
```

**데이터 CSV 제출 (개발자가 아닌 팀원)**
```
README.md 4장 규칙을 따라줘.
data/manual/payment_checks_<이름>.csv 파일을 이슈 #18로 제출하려고 해.
1. data/ 브랜치를 만들고
2. PRD 부록 C 템플릿과 컬럼·허용값이 맞는지 먼저 검사해서 틀린 행을 알려줘 (파일은 고치지 말고).
3. 문제가 없으면 data(qr) 형식으로 커밋하고 PR을 만들어줘. 리뷰어는 데이터 B와 개발 리드.
```

**충돌 해결**
```
PR에서 main과 충돌이 났어. main을 내 브랜치에 반영해서 충돌을 해결하고 싶어.
충돌 난 파일과 양쪽 내용을 먼저 보여주고, 어떻게 합칠지 제안만 해줘.
내 변경이 아닌 부분을 임의로 지우지 말고, force push는 하지 마.
```

**스키마 변경**
```
README.md 4.5 절차대로 스키마를 바꾸려고 해 (이슈 #25: merchant에 adm_dong_code 추가).
db/migrations/에 다음 번호의 마이그레이션 파일을 만들고, db/schema.sql도 같은 내용으로 갱신해줘.
이미 있는 마이그레이션 파일은 수정하지 마.
PRD 9.3에 추가할 변경 이력 한 줄도 같이 써줘.
```

**릴리스 태그**
```
main 최신 커밋에 v0.5-p0 태그를 달려고 해.
지난 태그 이후 머지된 PR 목록으로 릴리스 노트 초안을 만들어서 먼저 보여줘.
확인하면 태그를 만들고 GitHub Release로 올려줘.
```

**이력 점검 (제출 전)**
```
제출 전에 형상관리 상태를 점검해줘. 수정은 하지 말고 보고만 해줘.
- main에 PR 없이 들어간 커밋이 있는지
- 규칙에 안 맞는 커밋 메시지·브랜치 이름
- 열려 있는 PR과 오래된 브랜치
- 커밋된 파일 중 비밀값이나 개인정보로 보이는 것
- 마일스톤별 남은 이슈
```
